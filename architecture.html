PACS Graph 101 — how it all fits together

A layer-by-layer tour of a pedagogical knowledge-graph project, from the schema at the top to the GraphRAG agent at the bottom.

A Physical Access Control System answers one question millions of times a day: "Should this credential, at this reader, right now, open this door?" Every layer in this codebase exists to answer that question — and to make it answerable in increasingly powerful ways.

1 · The big picture

Seven layers, each one building on the last. None of them is large; the value is in how they compose.

2 · Layer 1 — Ontology (the contract)

The ontology is the schema: what kinds of things exist and what kinds of relationships can hold between them. It contains no data and makes no decisions. It tells you what shape the data takes and what shape the questions can take.

The eight classes

ClassWhat it is
PersonA human — employee, contractor, visitor
CredentialA badge, PIN, mobile key, or biometric template
ReaderThe device at a door that reads credentials
DoorA physical opening that can be locked / unlocked
ZoneA space behind one or more doors
AccessGroupA named bundle of permissions (e.g. "Employees")
ScheduleA time window (24x7, BusinessHours)
ControllerThe panel that makes grant / deny decisions for readers

The seven predicates (edge types)

PredicateDomain → RangeMeaning
holdsPerson → CredentialThis badge belongs to this person
member_ofPerson → AccessGroupThis person is in this group
grants_access_toAccessGroup → DoorThis group can open this door
active_duringAccessGroup → ScheduleThis group's access only applies then
controlsReader → DoorThis reader unlocks this door
protectsDoor → ZonePassing this door enters this zone
managed_byReader → ControllerThis panel owns this reader

The modeling decisions worth noticing

  • AccessGroup is the join table. Without it you'd connect every Person directly to every Door — quadratic edges. Groups make access manageable.
  • Schedule attaches to the group, not the person. The same person can be 24×7 via one group and 9-5 via another.
  • Zone vs Door. A door is the boundary; a zone is the space. You grant access to a door (the action), but you reason about who's in a zone (the state).
key idea The ontology is the contract every other layer is bound to. Adding a class or predicate is a four-place edit: ontology.md (document it), graph.json (use it), the JS reasoner/viewer (consume it), and neo4j/import.py + cypher.md (consume it). Don't add unused predicates.

4 · Layer 3 — Closed-form reasoner

The PACS decision in 80 lines of plain JavaScript. canAccess(graph, personId, doorId, atTime) walks the graph and returns whether to grant access — plus the path that justified it, or the reason it failed.

The rule, in words

GRANT iff there exists an AccessGroup G such that:

  Person  ─member_of─►       G
  G       ─grants_access_to► Door
  G       ─active_during─►   Schedule S
  S       covers atTime

Everything else is DENY.

The core traversal

reasoner.js (the inner loop)
export function canAccess(graph, personId, doorId, atTime) {
  const { neighbors } = buildIndex(graph);

  // For every group the person is in, check whether that group
  // grants this door AND its schedule covers `atTime`.
  for (const groupId of neighbors(personId, "member_of")) {
    const doors = neighbors(groupId, "grants_access_to");
    if (!doors.includes(doorId)) continue;

    for (const schedId of neighbors(groupId, "active_during")) {
      if (scheduleCovers(schedId, atTime)) {
        return {
          decision: "grant",
          path:  [personId, groupId, doorId, schedId],
          edges: [
            { from: personId, to: groupId, predicate: "member_of" },
            { from: groupId,  to: doorId,  predicate: "grants_access_to" },
            { from: groupId,  to: schedId, predicate: "active_during" }
          ],
          reason: `via group "${groupId}" on schedule "${schedId}"`
        };
      }
    }
  }
  /* ... diagnostic-deny logic below ... */
}

Two opinions baked in

  • Fail-closed. Unknown schedule → deny. Safety default. Never flip this to fail-open.
  • Diagnostic deny. Instead of returning a bare false, the reasoner runs three checks to identify which condition failed:
reasoner.js (diagnostic deny)
// 1. Is the person in any group?
const groups = neighbors(personId, "member_of");
if (groups.length === 0) {
  return { decision: "deny", reason: "person is in no AccessGroup" };
}

// 2. Of those groups, does any grant this door?
const granting = groups.filter(g =>
  neighbors(g, "grants_access_to").includes(doorId));
if (granting.length === 0) {
  return { decision: "deny", reason: "no group of this person grants this door" };
}

// 3. Otherwise, no covering schedule.
return {
  decision: "deny",
  reason: `group(s) ${granting.join(", ")} grant the door, but no schedule covers this time`
};
teaching point This is the topology + side condition pattern in its purest form. The path existing is necessary but not sufficient; the schedule check (a context-dependent side condition over atTime) is what turns a graph from a data structure into a policy engine.

Without grid-template-rows: minmax(0, 1fr), the side panel's scrollable content drives the row height past the viewport. The canvas grows with it, and network.fit() centers the view in the offscreen middle — blank screen, no errors. We debugged this once; don't undo it.

6 · Layer 5 — Neo4j (real graph database)

The JS reasoner answers one question shape. Cypher in Neo4j lets you ask anything you can compose. Same model, vastly more leverage.

Then docker compose up -d brings it up. Browser at localhost:7474 (login: neo4j / pacsgraph101).

Load the graph

The importer maps our JSON to Neo4j's labelled-property model: class becomes the node label, predicate becomes the relationship type.

neo4j/import.py (the core mapping)
# Nodes — one MERGE per class, label matches the `class` field
for cls, rows in by_class.items():
    s.run(
        f"UNWIND $rows AS row "
        f"MERGE (n:{cls} {{id: row.id}}) "
        f"SET   n.label = row.label",
        rows=rows,
    )

# Edges — CREATE (not MERGE) so the same (from, to, predicate) tuple
# can occur multiple times. Re-instatement creates a *second* edge.
for pred, rows in by_pred.items():
    s.run(
        f"UNWIND $rows AS row "
        f"MATCH (a {{id: row.from}}), (b {{id: row.to}}) "
        f"CREATE (a)-[r:{pred}]->(b) "
        f"SET r.valid_from = CASE WHEN row.valid_from IS NOT NULL "
        f"                        THEN date(row.valid_from) ELSE NULL END, "
        f"    r.valid_to   = CASE WHEN row.valid_to   IS NOT NULL "
        f"                        THEN date(row.valid_to)   ELSE NULL END",
        rows=rows,
    )
why CREATE, not MERGE MERGE would collapse two edges between the same nodes into one. Bob has two member_of edges to ContractorsDay — one closed, one open — because he was re-instated. MERGE would lose the gap. CREATE preserves it. Safe because import.py wipes the DB first; idempotency is preserved that way.

The reasoner, in Cypher

The entire canAccess from Layer 3, expressed in one query:

Cypher — equivalent of reasoner.js::canAccess
WITH datetime() AS now, 'alice' AS person_id, 'd_lab' AS door_id
MATCH (p:Person {id: person_id})-[:member_of]->(g:AccessGroup)
                                -[:grants_access_to]->(d:Door {id: door_id})
WHERE EXISTS {
  MATCH (g)-[:active_during]->(s:Schedule)
  WHERE date(now).dayOfWeek IN s.weekdays
    AND time(now).hour     >= s.start_hour
    AND time(now).hour     <  s.end_hour
}
RETURN p.label AS person, g.label AS via_group, d.label AS door;

Empty result = DENY. One or more rows = GRANT (and the row tells you which group justified it). Three new ideas this query introduces:

  1. WITH as parameter injection. Cypher's closest thing to function arguments.
  2. EXISTS { ... } as side-condition sub-query. True if the inner pattern has at least one match — the existence side-condition flavor.
  3. Cypher's temporal types. date(x).dayOfWeek, time(x).hour — first-class, ISO-8601 weekdays (Mon=1..Sun=7).
same data, different power The JS reasoner can only answer "grant or deny?". Cypher lets you ask: "Who is in more than one group?" "Which controllers manage readers that control no door?" "Show me the path from this credential to this zone." Same graph, infinitely more questions.

7 · Layer 6 — Temporal model

A snapshot graph can't answer the auditor's classic question: "Who had access at 2 AM on March 14th?" If revocation destroys the edge, the prior state is gone. The temporal model is the fix.

The principle

Every policy edge carries an optional validity window. Revocation is append-only — you close an edge by setting valid_to, never delete it.

  open edge:    valid_from = 2026-01-01, valid_to = null   ◄── still in force
  closed edge:  valid_from = 2026-01-01, valid_to = 2026-05-10

Which predicates are temporal?

PredicateTemporal?Why
holds✓Badges are issued and revoked
member_of✓Group memberships change
grants_access_to✓Policy is edited
active_during✓A group's schedule can be reassigned
controls✗ staticHardware wiring — changes slowly
protects✗ staticBuilding layout — same
managed_by✗ staticPanel topology — same

The live-at-$when filter

One pattern, applied to every temporal edge in a query, turns a snapshot query into a time-travel query:

Cypher — the foundational temporal filter
WHERE (r.valid_from IS NULL OR r.valid_from <= $when)
  AND (r.valid_to   IS NULL OR r.valid_to   >  $when)

Read aloud: "the edge started by $when (or has no start) AND hadn't ended by $when (or never ended)." Both must hold = the edge was live at $when.

The auditor's question, side by side

QueryResultWhy
WITH date() AS when ... (today) Carol only Alice's member_of closed 2026-05-10
WITH date('2026-04-15') AS when ... Alice + Carol On April 15, Alice was still a member

Same query shape. One literal changes. Two completely different answers. A legacy PACS that DELETEs revoked edges can produce the first answer but cannot produce the second at all — the data is gone.

Re-instatement: multiple edges, same nodes

Bob's contract ended 2026-04-15, then he came back 2026-04-22. That's two member_of edges between Bob and ContractorsDay with non-overlapping windows — never a reopening of the old one.

  bob ─member_of─► grp_con  [2026-01-01 → 2026-04-15]   ◄── closed (old contract)
  bob ─member_of─► grp_con  [2026-04-22 → null      ]   ◄── open (re-instatement)
                            └──── 7-day gap ────┘

Reopening the old edge by clearing valid_to would erase the gap and produce wrong answers for "was Bob a member on April 18?". The append-only model preserves the truth.

credentials are reissued, not reactivated When Bob returned, he got Badge-004 (a new Credential node), not a reactivation of Badge-002. Credentials are first-class identities; their history stays in the graph closed forever. This matches real PACS security policy.

8 · Layer 7 — GraphRAG agent

The agent turns English questions into Cypher, executes them, and renders prose answers. The architecture is dictated by one safety property: the LLM never sees the raw data while answering the user's question.

The two-call pattern

  user question
       │
       ▼
  ┌───────────────────────┐
  │  Claude #1 — Planner  │ ◄── system prompt: ontology.md
  │                       │
  │  sees:  schema only   │
  │  emits: ONE Cypher    │
  └───────────────────────┘
       │
       ▼
   cypher string
       │
       ▼
  ┌───────────────────────┐
  │  Safety regex gate    │  rejects DELETE/MERGE/SET/CREATE/...
  └───────────────────────┘
       │ (read-only verbs only)
       ▼
  ┌───────────────────────┐
  │  Neo4j session        │  default_access_mode="r"
  │                       │  (driver-level read enforcement)
  └───────────────────────┘
       │
       ▼
    rows (JSON)
       │
       ▼
  ┌───────────────────────┐
  │  Claude #2 — Renderer │ ◄── system prompt: stable
  │                       │
  │  sees:  question +    │
  │         cypher + rows │
  │  emits: prose answer  │
  └───────────────────────┘
       │
       ▼
  user sees: plan, rows, answer
  saved to:  agent/transcripts/<ts>/

Why two separate calls, not one

If a single LLM saw both the question and the rows, it could "blend" — reinterpret rows to match what it expected. Keeping the calls separate enforces a hard property: the renderer trusts the rows. It can't compose new queries; it can only describe what's there.

The planner call

agent/agent.py (planner)
def call_planner(client, planner_system, question, today):
    user_msg = f"TODAY={today}\n\nQuestion: {question}"
    response = client.messages.create(
        model="claude-opus-4-7",
        max_tokens=16000,
        thinking={"type": "adaptive"},
        output_config={"effort": "high"},
        system=[{
            "type": "text",
            "text": planner_system,
            # Stable system prompt → caches across questions. Volatile
            # bits (today, the question) live in the user message so the
            # cache prefix never shifts.
            "cache_control": {"type": "ephemeral"},
        }],
        messages=[{"role": "user", "content": user_msg}],
    )
    return "".join(b.text for b in response.content if b.type == "text")

The safety gate

agent/agent.py (forbidden verbs)
FORBIDDEN = re.compile(
    r"\b(?:CREATE|MERGE|DELETE|DETACH|SET|REMOVE|DROP|LOAD\s+CSV|"
    r"CALL\s+(?!{)|FOREACH)\b",
    flags=re.IGNORECASE,
)

def safety_check(cypher: str) -> str | None:
    if FORBIDDEN.search(cypher):
        match = FORBIDDEN.search(cypher).group(0)
        return f"query contains forbidden write keyword: {match!r}"
    return None

Belt-and-braces with the driver:

agent/agent.py (read-only session)
def run_cypher(driver, cypher):
    # Even if the regex were bypassed, the driver refuses writes
    # in a read-mode session. Defense in depth.
    with driver.session(default_access_mode="r") as session:
        result = session.run(cypher)
        return [record.data() for record in result]

The planner system prompt — built from the live ontology

agent/prompts.py (composition)
def build_planner_system(ontology_text: str) -> str:
    """Compose the planner system prompt with the live ontology contents.

    Keep this pure — same `ontology_text` must produce the same bytes
    every call so prompt caching stays warm.
    """
    return PLANNER_INTRO + ontology_text + PLANNER_OUTRO

The system prompt embeds ontology.md verbatim. The planner sees the contract, never the data. This is the schema-aware grounding that distinguishes GraphRAG from naive RAG: it doesn't search through chunks — it composes queries from a known schema.

prompt caching is load-bearing The planner system prompt is hundreds of lines (intro + ontology + temporal model + style notes). Without caching, every question pays for sending all of it again. With cache_control: {"type": "ephemeral"}, subsequent questions are ~90% cheaper. The volatile bits (today's date, the user's question) live in the user message so the cached prefix never shifts.

Transcripts — Phase 4 fuel

Each question saves four files under agent/transcripts/<timestamp>/:

  agent/transcripts/2026-05-24T14-32-07/
  ├── question.txt    ← the English question
  ├── plan.cypher     ← what the planner emitted
  ├── rows.json       ← what Neo4j returned
  └── answer.txt      ← what the renderer produced

These artifacts are the input to the deferred Phase 4: a head-to-head comparison against the same questions written in SQL. The point isn't "GraphRAG wins"; it's here's the question shape that needs it, and here's what it still gets wrong.

10 · Invariants that hold across the stack

These aren't enforced by tests (there are none). They're enforced by discipline and documented in CLAUDE.md so future sessions don't regress them.

InvariantLives inWhy it matters
Ontology is the contract ontology.md → graph.json → reasoner.js / index.html / import.py / cypher.md Adding a predicate is a four-place edit. Top-down propagation is the discipline.
Fail-closed on unknown schedules reasoner.js::scheduleCovers Security default — if we don't recognise the schedule, deny.
Diagnostic deny canAccess + the agent renderer Operators need to know why access failed, not just that it failed.
Append-only on policy edges graph.json, import.py, cypher.md, scenarios.md Revocation must preserve history. Never DELETE; close with valid_to.
Live-at-$when filter pattern cypher.md §6, scenarios.md, agent planner prompt Single foundational pattern for every audit-style query.
Credentials are reissued, not reactivated graph.json (Bob → Badge-004), ontology.md Matches real PACS security; credential ID has its own lifetime.
Planner and renderer never overlap agent.py (two separate LLM calls) The renderer can't compose queries; the planner can't see data.
Read-only enforcement, two places agent.py regex + Neo4j session mode Defense in depth. Either alone would suffice; both together is the right level of paranoia.
Prompt caching prefix is stable agent.py + prompts.py Today's date and the question go in the user message, not system. Don't add timestamps to the system prompt.

11 · Where to go next

Deferred (Phase 4) — GraphRAG vs SQL

The most pedagogically valuable next step is the honest comparison. Plain RAG over markdown chunks is a strawman — PACS data never lives that way in reality. The real incumbent is a relational database with valid_from / valid_to columns on every junction table.

The Phase 4 we'd actually want to build:

  • A Postgres or SQLite mirror with cardholder, access_group_membership, access_level_assignment tables
  • The same canonical questions written as both Cypher (via the GraphRAG agent) and SQL
  • An honest comparison: where SQL wins (well-known, mature tooling, performance), where it gets painful (re-instatement, gap detection, multi-temporal joins), and where it's a wash
