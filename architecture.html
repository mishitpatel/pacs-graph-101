PACS Graph 101 — how it all fits together

A layer-by-layer tour of a pedagogical knowledge-graph project, ending in a deep dive of the GraphRAG agent.

A Physical Access Control System answers one question millions of times a day: "Should this credential, at this reader, right now, open this door?" Every layer in this codebase exists to answer that question — and to make it answerable in increasingly powerful ways.

1 · The big picture

Five layers, each one building on the last. None of them is large; the value is in how they compose.

   ┌───────────────────────────────────────────────────────┐

2 · Layer 1 — Ontology (the contract)

The ontology is the schema: what kinds of things exist and what kinds of relationships can hold between them. It contains no data and makes no decisions. It tells you what shape the data takes and what shape the questions can take.

The eight classes

ClassWhat it is
PersonA human — employee, contractor, visitor
CredentialA badge, PIN, mobile key, or biometric template
ReaderThe device at a door that reads credentials
DoorA physical opening that can be locked / unlocked
ZoneA space behind one or more doors
AccessGroupA named bundle of permissions (e.g. "Employees")
ScheduleA time window (24x7, BusinessHours)
ControllerThe panel that makes grant / deny decisions for readers

The seven predicates (edge types)

PredicateDomain → RangeMeaning
holdsPerson → CredentialThis badge belongs to this person
member_ofPerson → AccessGroupThis person is in this group
grants_access_toAccessGroup → DoorThis group can open this door
active_duringAccessGroup → ScheduleThis group's access only applies then
controlsReader → DoorThis reader unlocks this door
protectsDoor → ZonePassing this door enters this zone
managed_byReader → ControllerThis panel owns this reader

The modeling decisions worth noticing

  • AccessGroup is the join table. Without it you'd connect every Person directly to every Door — quadratic edges. Groups make access manageable.
  • Schedule attaches to the group, not the person. The same person can be 24×7 via one group and 9-5 via another.
  • Zone vs Door. A door is the boundary; a zone is the space. You grant access to a door (the action), but you reason about who's in a zone (the state).
key idea The ontology is the contract every other layer is bound to. Adding a class or predicate is a three-place edit: ontology.md (document it + why), graph.json (use it), and neo4j/import.py + cypher.md (consume it). Don't add unused predicates.

The seeded population

Three people, intentionally chosen so worked examples have a clean shape:

PersonGroupsDoorsWhy interesting
AliceEmployees (closed 2026-05-10)Front, LabDemonstrates revocation — was active, now closed

The decision rule, in words

The PACS authorization rule has the same shape no matter which layer expresses it:

GRANT iff there exists an AccessGroup G such that:

  Person  ─member_of─►       G
  G       ─grants_access_to► Door
  G       ─active_during─►   Schedule S
  S       covers atTime

Everything else is DENY.

Four conditions joined by AND. The first three are structural (paths through edges). The fourth is a side condition over context (the current time). This composition — topology + side condition — is the canonical shape of every interesting question in this project. Layer 3 expresses it in Cypher; Layer 4 generalizes it temporally; Layer 5 has an LLM compose it.

design note Edges can have optional valid_from / valid_to properties — the temporal model. We'll come back to this in Layer 4. For now: edges with no validity are treated as always valid; edges with valid_to set are closed.

Load the graph

The importer maps our JSON to Neo4j's labelled-property model: class becomes the node label, predicate becomes the relationship type.

neo4j/import.py (the core mapping)
# Nodes — one MERGE per class, label matches the `class` field
for cls, rows in by_class.items():
    s.run(
        f"UNWIND $rows AS row "
        f"MERGE (n:{cls} {{id: row.id}}) "
        f"SET   n.label = row.label",
        rows=rows,
    )

# Edges — CREATE (not MERGE) so the same (from, to, predicate) tuple
# can occur multiple times. Re-instatement creates a *second* edge.
for pred, rows in by_pred.items():
    s.run(
        f"UNWIND $rows AS row "
        f"MATCH (a {{id: row.from}}), (b {{id: row.to}}) "
        f"CREATE (a)-[r:{pred}]->(b) "
        f"SET r.valid_from = CASE WHEN row.valid_from IS NOT NULL "
        f"                        THEN date(row.valid_from) ELSE NULL END, "
        f"    r.valid_to   = CASE WHEN row.valid_to   IS NOT NULL "
        f"                        THEN date(row.valid_to)   ELSE NULL END",
        rows=rows,
    )
why CREATE, not MERGE MERGE would collapse two edges between the same nodes into one. Bob has two member_of edges to ContractorsDay — one closed, one open — because he was re-instated. MERGE would lose the gap. CREATE preserves it. Safe because import.py wipes the DB first; idempotency is preserved that way.

The decision rule, in Cypher

The four-edge rule from Layer 2, expressed as one query:

Cypher — the canonical access decision
WITH datetime() AS now, 'alice' AS person_id, 'd_lab' AS door_id
MATCH (p:Person {id: person_id})-[:member_of]->(g:AccessGroup)
                                -[:grants_access_to]->(d:Door {id: door_id})
WHERE EXISTS {
  MATCH (g)-[:active_during]->(s:Schedule)
  WHERE date(now).dayOfWeek IN s.weekdays
    AND time(now).hour     >= s.start_hour
    AND time(now).hour     <  s.end_hour
}
RETURN p.label AS person, g.label AS via_group, d.label AS door;

Empty result = DENY. One or more rows = GRANT (and the row tells you which group justified it). Three new ideas this query introduces:

  1. WITH as parameter injection. Cypher's closest thing to function arguments.
  2. EXISTS { ... } as side-condition sub-query. True if the inner pattern has at least one match — the existence side-condition flavor.
  3. Cypher's temporal types. date(x).dayOfWeek, time(x).hour — first-class, ISO-8601 weekdays (Mon=1..Sun=7).

Side-condition flavors you can compose in Cypher

FlavorExample use
Temporalschedule covers a given moment
Propertyg.id = 'grp_emp'
ExistenceWHERE EXISTS { ... }
Cardinalitycount(g) > 1 — "people in more than one group"
Disjunctiondoor protects either Zone X or Zone Y
NegationNOT EXISTS { ... } — integrity checks
Variable-length path[*1..6] — reachability

See neo4j/cypher.md for a worked example of each.

same data, different power The pattern stays the same — structural match + side condition(s) — but the question can be anything. "Who is in more than one group?" "Which controllers manage readers that control no door?" "Show me the path from this credential to this zone." Same graph, infinitely more questions.

5 · Layer 4 — Temporal model

A snapshot graph can't answer the auditor's classic question: "Who had access at 2 AM on March 14th?" If revocation destroys the edge, the prior state is gone. The temporal model is the fix.

The principle

Every policy edge carries an optional validity window. Revocation is append-only — you close an edge by setting valid_to, never delete it.

  open edge:    valid_from = 2026-01-01, valid_to = null   ◄── still in force
  closed edge:  valid_from = 2026-01-01, valid_to = 2026-05-10

Which predicates are temporal?

PredicateTemporal?Why
holds✓Badges are issued and revoked
member_of✓Group memberships change
grants_access_to✓Policy is edited
active_during✓A group's schedule can be reassigned
controls✗ staticHardware wiring — changes slowly
protects✗ staticBuilding layout — same
managed_by✗ staticPanel topology — same

The live-at-$when filter

One pattern, applied to every temporal edge in a query, turns a snapshot query into a time-travel query:

Cypher — the foundational temporal filter
WHERE (r.valid_from IS NULL OR r.valid_from <= $when)
  AND (r.valid_to   IS NULL OR r.valid_to   >  $when)

Read aloud: "the edge started by $when (or has no start) AND hadn't ended by $when (or never ended)." Both must hold = the edge was live at $when.

The auditor's question, side by side

QueryResultWhy
WITH date() AS when ... (today) Carol only Alice's member_of closed 2026-05-10
WITH date('2026-04-15') AS when ... Alice + Carol On April 15, Alice was still a member

Same query shape. One literal changes. Two completely different answers. A legacy PACS that DELETEs revoked edges can produce the first answer but cannot produce the second at all — the data is gone.

Re-instatement: multiple edges, same nodes

Bob's contract ended 2026-04-15, then he came back 2026-04-22. That's two member_of edges between Bob and ContractorsDay with non-overlapping windows — never a reopening of the old one.

  bob ─member_of─► grp_con  [2026-01-01 → 2026-04-15]   ◄── closed (old contract)
  bob ─member_of─► grp_con  [2026-04-22 → null      ]   ◄── open (re-instatement)
                            └──── 7-day gap ────┘

Reopening the old edge by clearing valid_to would erase the gap and produce wrong answers for "was Bob a member on April 18?". The append-only model preserves the truth.

credentials are reissued, not reactivated When Bob returned, he got Badge-004 (a new Credential node), not a reactivation of Badge-002. Credentials are first-class identities; their history stays in the graph closed forever. This matches real PACS security policy.

6 · Layer 5 — GraphRAG agent

The agent turns English questions into Cypher, executes them, and renders prose answers. The architecture is dictated by one safety property: the LLM never sees the raw data while answering the user's question. The rest of this section is a deep dive — every named piece, every parameter, every "why this way."

6.1 · Skeleton & entry point

When you run python3 agent/agent.py, Python jumps to the bottom of the file:

if __name__ == "__main__":
    sys.exit(repl())

repl() is the entire program. Everything else in the file is machinery that repl() calls. Here's the skeleton with print-formatting stripped:

agent/agent.py (the bones of repl)
def repl() -> int:
    # 0. Preflight
    today          = datetime.now().date().isoformat()
    client         = anthropic.Anthropic()
    planner_system = prompts.build_planner_system(prompts.read_ontology(REPO_ROOT))
    driver         = GraphDatabase.driver(NEO4J_URI, auth=(NEO4J_USER, NEO4J_PASSWORD))
    driver.verify_connectivity()

    while True:
        question = input("? ").strip()
        if not question:        continue
        if question == "exit":  break

        # 1. Plan       (LLM call #1)
        plan_text = call_planner(client, planner_system, question, today)
        cypher    = extract_cypher(plan_text)

        # 2. Safety
        if reason := safety_check(cypher):
            print(f"REJECTED — {reason}"); continue

        # 3. Execute    (Neo4j)
        rows = run_cypher(driver, cypher)

        # 4. Render     (LLM call #2)
        answer = call_renderer(client, question, cypher, rows)

        # 5. Save
        save_transcript(question, cypher, rows, answer)

    driver.close()
    return 0

Three things to notice before we go deeper:

  • Setup once, loop forever. planner_system is built once. The Anthropic client and Neo4j driver are created once and reused. That's a prerequisite for prompt caching to work (§6.7).
  • Five named steps, ordered, no skipping. Plan → Safety → Execute → Render → Save. Safety is between plan and execute — a gate, not an afterthought.
  • Errors don't crash the loop. Each LLM call and the Neo4j call sit inside try/except in the real code; on error the loop continues so one bad question doesn't kill the session.

6.2 · Prompts: what's stable, what's volatile

agent/prompts.py has two halves:

prompts.py
├── PLANNER_INTRO        ◄── string constant: role + output format
├── PLANNER_OUTRO        ◄── string constant: ontology-adjacent details + style notes
├── RENDERER_SYSTEM      ◄── string constant: the entire renderer prompt
├── build_planner_system(ontology_text) → str     # composes the planner prompt
└── read_ontology(repo_root)            → str     # reads ontology.md

The planner system prompt has a specific structure:

  PLANNER_INTRO  +  ontology.md  +  PLANNER_OUTRO
  ─────────────    ─────────────    ─────────────
  stable           stable per       stable
  (project life)   session          (project life)

All three parts are stable across questions. That's the cache property. The planner system prompt is byte-for-byte identical from question 1 to question 100 within a session.

What's volatile — today's date, the question itself — goes in the user message, not the system prompt. That's the rule: anything that varies per request must live below the last cache_control breakpoint.

PLANNER_INTRO — role and output contract

agent/prompts.py
PLANNER_INTRO = """\
You are a read-only Cypher planner for the PACS knowledge graph.

Your job: given a question in English, output exactly ONE Cypher query
that answers it against the schema below. Nothing else.

# Output format

Return ONLY the Cypher query, wrapped in a ```cypher fenced code block.
No prose, no explanation, no "Here's the query:" preamble. ...
The query MUST be read-only ...
Do NOT use any of: CREATE, MERGE, DELETE, DETACH, SET, REMOVE, DROP,
LOAD CSV, CALL, FOREACH.

# The PACS schema
"""

Three jobs:

  1. Role assignment. A narrow role ("plan one query") produces tighter outputs than a broad one.
  2. Output contract. "Wrap in a ```cypher block." This is what makes the regex extractor reliable.
  3. Forbidden verbs declared upfront. Same list as the safety gate — but having the LLM know in advance means most rejections never happen.

PLANNER_OUTRO — everything the schema alone doesn't tell you

The intro tells the planner what to do. The outro fills in what ontology.md alone leaves out:

BlockWhat it teaches
Schedule propertiesSchedule nodes have weekdays, start_hour, end_hour — set by import.py, not in the ontology proper
Temporal modelWhich predicates carry validity windows, plus the live-at-$when filter verbatim, plus the rule "don't add the filter when asking about history"
Date function referenceA short reference card for date(), datetime(), duration.inDays(), coalesce()
Style notes & gotchas"Use DISTINCT when joining multiple temporal edges," "TODAY=YYYY-MM-DD arrives in the user message," "holds points Person→Credential so reverse the arrow if you start at Credential"

Each line in that last block came from a real bug. The DISTINCT rule was added because the planner would otherwise duplicate Carol's row. The arrow-direction note came from a debug session. A system prompt evolves like this: bugs become rules. Every line earns its keep.

RENDERER_SYSTEM — the prose layer

agent/prompts.py
RENDERER_SYSTEM = """\
You translate Neo4j Cypher query results into clear English answers
for a security/audit operator working with a PACS knowledge graph.

# What you receive (in the user message)
- The user's original question.
- The Cypher query that was run (for transparency only).
- The rows it returned, as JSON.

# How to answer
- 2-4 sentences. Plain English. Direct.
- If the rows are empty, say so plainly AND explain what that means in
  context. "No one had access. (Empty result confirms the assertion holds.)"
- If a row contains a date range, mention the dates explicitly when
  they're material to the answer.
- If multiple rows have the same person/entity with different time
  windows (e.g. re-instatement), call that out.
- Do NOT invent information that isn't in the rows.
- Do NOT hedge or add disclaimers. The rows are ground truth.

# Tone
Confident, concise, audit-grade. You are not a chatbot; you are a
reporting layer over a deterministic query.
"""

The renderer system prompt is also stable; only the user message varies per call. The three rules that matter most:

  • Empty-result rule. In Cypher, empty is often the correct answer. Without this rule the renderer would hedge.
  • Anti-hallucination rule. "Do NOT invent information that isn't in the rows." The renderer is a reporting layer over a deterministic query. It can't speculate.
  • Tone calibration. "Audit-grade" — confident and dateful, not chatbot-y.

The composition function

agent/prompts.py
def build_planner_system(ontology_text: str) -> str:
    """Compose the planner system prompt with the live ontology contents.

    Keep this function pure — the same `ontology_text` must produce the
    same bytes every call so prompt caching stays warm.
    """
    return PLANNER_INTRO + ontology_text + PLANNER_OUTRO


def read_ontology(repo_root: Path) -> str:
    """Read ontology.md and strip trailing whitespace for cache stability."""
    text = (repo_root / "ontology.md").read_text(encoding="utf-8")
    return text.rstrip() + "\n"

Two non-obvious choices in read_ontology:

  • encoding="utf-8" is explicit — same bytes regardless of platform locale.
  • rstrip() + "\n" normalizes the trailing newline — if a different editor saved the file with/without a trailing newline, the cache prefix would shift by a single byte and invalidate everything.

6.3 · The planner call

agent/agent.py
def call_planner(client, planner_system, question, today):
    user_msg = f"TODAY={today}\n\nQuestion: {question}"
    response = client.messages.create(
        model="claude-opus-4-7",          # ← latest Opus
        max_tokens=16000,                 # ← generous ceiling
        thinking={"type": "adaptive"},    # ← model chooses when to think
        output_config={"effort": "high"}, # ← thoroughness vs cost knob
        system=[{
            "type": "text",
            "text": planner_system,
            "cache_control": {"type": "ephemeral"},   # ← cache breakpoint
        }],
        messages=[{"role": "user", "content": user_msg}],
    )
    return "".join(b.text for b in response.content if b.type == "text")

Five things to understand:

  1. The user message holds the volatile context. Today's date and the question are the only parts that vary. They live in the user message, never in the system prompt — that's what keeps the cache prefix stable.
  2. thinking={"type": "adaptive"} — the model decides when to think internally. Simple questions skip it; "find the gap between Bob's two stints" gets thinking. You pay only for what's used.
  3. output_config={"effort": "high"} — controls thoroughness. Default and sweet spot for intelligence-sensitive work on Opus 4.7.
  4. system is an array of typed blocks. The simple form (system="...") can't carry cache_control; the list form is the minimum way to mark something cacheable.
  5. cache_control: {"type": "ephemeral"} — the magic. Everything before this breakpoint becomes the cacheable prefix. We unpack the full picture in §6.7.

The response-parsing line is doing real work:

return "".join(b.text for b in response.content if b.type == "text")

response.content is a list of content blocks. With adaptive thinking enabled, the response can also contain thinking blocks (text empty by default; opt in with display: "summarized" if you want them visible). We filter to text blocks and concatenate.

Extracting the Cypher from the response

agent/agent.py
CYPHER_BLOCK = re.compile(r"```(?:cypher|cypher\s*)?\n?(.*?)```", flags=re.DOTALL)

def extract_cypher(text: str) -> str:
    """Pull a single Cypher block out of the planner's response."""
    matches = CYPHER_BLOCK.findall(text)
    if not matches:
        return text.strip()   # fallback: maybe bare Cypher
    return matches[0].strip()

The planner is told to emit fenced blocks and almost always complies. The fallback handles the case where it returns bare text instead. re.DOTALL makes . match newlines so multi-line Cypher captures cleanly.

6.4 · The safety gate

agent/agent.py
FORBIDDEN = re.compile(
    r"\b(?:CREATE|MERGE|DELETE|DETACH|SET|REMOVE|DROP|LOAD\s+CSV|"
    r"CALL\s+(?!{)|FOREACH)\b",
    flags=re.IGNORECASE,
)

def safety_check(cypher: str) -> str | None:
    """Return None if safe, else a human-readable reason."""
    if FORBIDDEN.search(cypher):
        match = FORBIDDEN.search(cypher).group(0)
        return f"query contains forbidden write keyword: {match!r}"
    return None

Two non-obvious regex details:

  • \b ... \b — word boundaries. Without them, CREATE would match inside identifiers like createdAt or comments.
  • CALL\s+(?!{) — negative lookahead. Cypher has two CALLs: CALL apoc.do.delete(...) invokes procedures (some write); CALL { ... } is a read-only sub-query. The (?!{) lets sub-query syntax through while rejecting procedure calls.

The function returns None on success and a reason string on failure — a common Python idiom where None means "no problem found." The REPL caller uses if reason := safety_check(cypher): print(...) — the walrus operator captures the reason and tests its truthiness in one expression.

6.5 · The executor

agent/agent.py
def run_cypher(driver, cypher):
    """Execute a Cypher query against a read-only session."""
    with driver.session(default_access_mode="r") as session:
        result = session.run(cypher)
        return [record.data() for record in result]

Tiny function, three important details:

  • default_access_mode="r" — the driver tells Neo4j: "this session is read-only." If a write somehow slipped past the regex, Neo4j itself refuses the query. Defense in depth.
  • record.data() — flattens to a plain dict of primitives + dates. Neo4j records can hold Node objects, Relationship objects, paths — none of which JSON-serialize cleanly. .data() normalizes everything.
  • List comprehension eager-loads. Fine for our toy graph; for a production graph you'd want pagination or a LIMIT clause.
two safety properties, one architecture The agent cannot mutate the graph for two independent reasons. (1) The regex gate rejects writes textually before they ever reach Neo4j. (2) The Neo4j session refuses writes by mode at the driver level. Either alone would suffice; both together is the right level of paranoia.

6.6 · The renderer call

agent/agent.py
def call_renderer(client, question, cypher, rows):
    user_msg = (
        f"Question: {question}\n\n"
        f"Cypher run:\n```cypher\n{cypher}\n```\n\n"
        f"Rows returned ({len(rows)}):\n{json.dumps(rows, default=str, indent=2)}"
    )
    response = client.messages.create(
        model="claude-opus-4-7",
        max_tokens=16000,
        thinking={"type": "adaptive"},
        output_config={"effort": "high"},
        system=[{
            "type": "text",
            "text": prompts.RENDERER_SYSTEM,
            "cache_control": {"type": "ephemeral"},
        }],
        messages=[{"role": "user", "content": user_msg}],
    )
    return "".join(b.text for b in response.content if b.type == "text").strip()

Structurally identical to the planner call. What differs:

  • System prompt is RENDERER_SYSTEM (stable for caching too).
  • User message carries three pieces: question, the Cypher that ran, and the rows as JSON.
  • json.dumps(rows, default=str, indent=2) — default=str handles Neo4j's date type by calling str() on it ("2026-04-15"). indent=2 pretty-prints so the renderer can reason about row groupings.

The safety property of this call is what the renderer can't see: the schema, the database connection, the planner prompt. It only sees the question, the Cypher that ran, and the rows. The Cypher is for transparency only; the renderer has no machinery to modify it or re-query.

6.7 · Prompt caching — how it works and why it's needed

Without caching, every question pays to re-transmit and re-process the same ~2000-token system prompt:

Q1:  system: 2000 tok  +  question: 30 tok  ──►  bill: 2030 tok input
Q2:  system: 2000 tok  +  question: 30 tok  ──►  bill: 2030 tok input
Q10: ...
                                    Total billed: ~20,300 tokens
                                    Of which redundant: ~18,000

The system prompt is byte-for-byte identical across all 10 calls. Caching turns redundant transmission into a near-free lookup.

How the cache works mechanically: prefix match

The Anthropic cache is a prefix match, not a content hash of the whole request. The request gets rendered in this fixed order:

┌─────────┐  ┌──────────┐  ┌────────────┐
│  tools  │  │  system  │  │  messages  │
└─────────┘  └──────────┘  └────────────┘
                  ▲
        cache_control breakpoint goes here
        means "cache everything up to AND including this point"

The breakpoint marks where the cacheable prefix ends. Anything before is hashed and matched against the cache; anything after is sent fresh every request.

                    cacheable prefix                    volatile suffix
        ┌──────────────────────────────────┐   ┌────────────────────┐
Req 1:  │ system: PLANNER_INTRO + ontology │ │ │ user: "TODAY=...   │
        │           + PLANNER_OUTRO        │   │       Question: …" │
        │       [cache_control here]       │   │                    │
        └──────────────────────────────────┘   └────────────────────┘
                            │
                            ▼
                  CACHE WRITE on the first call
                  (~125% of normal cost on these tokens)

                    same exact bytes                    different bytes
        ┌──────────────────────────────────┐   ┌────────────────────┐
Req 2:  │ ...identical bytes...            │ │ │ user: "TODAY=...   │
        │       [cache_control here]       │   │       Question: …" │
        └──────────────────────────────────┘   └────────────────────┘
                            │
                            ▼
                  CACHE READ — match!
                  (~10% of normal cost on these tokens)

Why prefix-match, not full content-match

LLMs process input autoregressively, left to right. The internal state the model accumulates over the first 2000 tokens is identical regardless of what question follows. Anthropic can stash that intermediate state on their servers, keyed by the prefix's hash, and load it instead of recomputing. One byte difference anywhere in the prefix → different cache key → no hit. No partial matches.

What it costs and saves

OperationCost per 1M tokens (Opus 4.7)Multiplier
Normal input$5.001.0×
Cache write (first time)$6.251.25×
Cache read (subsequent)$0.500.10×
Normal output$25.001.0×

The math for our agent: 10 questions, ~2000-token system prompt.

  • Without caching: 10 × 2000 × $5/M = $0.10 on the system prompt alone.
  • With caching: 1 write (2000 × 1.25 = 2500) + 9 reads (2000 × 0.10 × 9 = 1800) = 4300 effective tokens × $5/M = $0.022.
  • Savings: ~80% reduction. Break-even: after the 2nd request.

The 5-minute TTL

ephemeral caches have a 5-minute time-to-live, refreshed on each hit. Interactive sessions stay hot because every hit resets the clock. There's a {"type": "ephemeral", "ttl": "1h"} option for batch processes that fire one question per minute. For our REPL the default is fine.

Silent invalidators — the bugs you can't see

The worst thing about prompt caching is that misuses don't fail. They just don't cache. Classic invalidators that look harmless:

# BAD — every request gets a fresh timestamp in the prefix
system = f"You are an assistant. Current time: {datetime.now()}"

# BAD — every request gets a fresh request ID
system = f"Request {uuid.uuid4()}: You are an assistant..."

# BAD — dict iteration order isn't guaranteed across runs
system = f"Schema:\n{json.dumps(schema_dict)}"   # JSON keys can reorder

# BAD — different file encoding produces different bytes on Windows
text = open("ontology.md").read()                # no encoding=, locale-dependent

Our read_ontology() and build_planner_system() defend against all of these — explicit encoding, normalized trailing newline, no clock or randomness in the composition.

How to verify caching is actually working

Verify with usage fields on the response
response = client.messages.create(...)

print(response.usage.input_tokens)                # uncached tokens (full price)
print(response.usage.cache_creation_input_tokens) # tokens written to cache (1.25×)
print(response.usage.cache_read_input_tokens)     # tokens served from cache (0.10×)

Expected pattern across a session:

Q1:  input_tokens=30, cache_creation=2000, cache_read=0
Q2:  input_tokens=30, cache_creation=0,    cache_read=2000
Q3:  input_tokens=30, cache_creation=0,    cache_read=2000
...

If cache_read=0 on every question, a silent invalidator is at work. Audit: dynamic content in the system prompt, inconsistent file encoding, or 5-minute TTL gaps between calls.

the rule you can keep in your head Stable content goes before the breakpoint; volatile content after. That's the entire design principle. Our agent.py follows it religiously: stable system prompt built from PLANNER_INTRO + ontology + PLANNER_OUTRO, volatile TODAY=... + question in the user message, cache_control exactly on the system block. Every design choice in prompts.py and call_planner exists to keep that prefix stable.

6.8 · Transcripts & the REPL loop

agent/agent.py
def save_transcript(question, cypher, rows, answer):
    """Save a per-turn folder with the four artifacts."""
    TRANSCRIPT_DIR.mkdir(parents=True, exist_ok=True)
    folder = TRANSCRIPT_DIR / datetime.now().strftime("%Y-%m-%dT%H-%M-%S")
    folder.mkdir(exist_ok=True)
    (folder / "question.txt").write_text(question + "\n", encoding="utf-8")
    (folder / "plan.cypher").write_text(cypher + "\n",   encoding="utf-8")
    (folder / "rows.json"   ).write_text(json.dumps(rows, default=str, indent=2) + "\n", encoding="utf-8")
    (folder / "answer.txt"  ).write_text(answer + "\n",  encoding="utf-8")
    return folder

One folder per question, named with an ISO-timestamp slug. Four files because each artifact serves a different consumer:

FileRead by
question.txtA human reviewing transcripts
plan.cypherA future Phase 4 diff against the SQL-equivalent
rows.jsonAnyone reproducing the answer offline
answer.txtThe "what did the user actually see" record

The folder is the unit of replay. If a question gets a wrong answer, you can re-run the renderer against rows.json to test whether prompt tweaks improve things — without re-running the planner or hitting Neo4j.

The REPL with error handling

agent/agent.py (the loop, with try/except)
while True:
    try:
        question = input(f"\n{CYAN}?{RESET} ").strip()
    except (EOFError, KeyboardInterrupt):
        print(); break
    if not question:                              continue
    if question.lower() in ("exit","quit",":q"):  break

    # 1. Plan
    try:
        plan_text = call_planner(client, planner_system, question, today)
    except anthropic.APIError as e:
        print(f"{RED}Planner failed: {e}{RESET}"); continue
    cypher = extract_cypher(plan_text)

    # 2. Safety
    if reason := safety_check(cypher):
        print(f"{RED}REJECTED — {reason}{RESET}"); continue

    # 3. Execute
    try:
        rows = run_cypher(driver, cypher)
    except Exception as e:
        print(f"{RED}Neo4j error: {e}{RESET}")
        save_transcript(question, cypher, [], f"[neo4j error] {e}")
        continue

    # 4. Render
    try:
        answer = call_renderer(client, question, cypher, rows)
    except anthropic.APIError as e:
        print(f"{RED}Renderer failed: {e}{RESET}"); continue

    # 5. Save
    save_transcript(question, cypher, rows, answer)

Structural rule: continue on every failure. The REPL is interactive — a flake on one question shouldn't kill the session. The user rephrases and tries again.

The one place we save despite a failure is Neo4j errors:

save_transcript(question, cypher, [], f"[neo4j error] {e}")

We save the broken Cypher + the error message. That's a future Phase 4 finding: the planner emitted Cypher that didn't execute. We want to know about it. Other failure modes (rate limit, network) aren't pedagogically interesting.

That's the whole agent. ~280 lines, every one of them doing a specific job, with the safety properties physically separated from the LLM (in regex, in driver config, in code architecture) rather than relying on the LLM to behave well.

9 · Where to go next

Next phase — GraphRAG vs SQL

The most pedagogically valuable next step is the honest comparison. Plain RAG over markdown chunks is a strawman — PACS data never lives that way in reality. The real incumbent is a relational database with valid_from / valid_to columns on every junction table.

What we'd build:

  • A Postgres or SQLite mirror with cardholder, access_group_membership, access_level_assignment tables — same data, relational shape
  • The same canonical questions written as both Cypher (via the agent) and SQL
  • An honest analysis: where SQL is better (well-known, mature tooling, predictable performance), where it gets painful (re-instatement modelling, gap detection, multi-temporal joins), and where it's a wash
